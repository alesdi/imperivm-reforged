# `.vs` host API inventory

**Status:** complete static inventory of the shipped corpus; semantics inferred, not proven
**Language:** [`vs-language.md`](vs-language.md)
**Extractor:** [`src/imperivm/formats/vs_parse.py`](../../src/imperivm/formats/vs_parse.py) — `python3 vs_parse.py --pack data.pak --api`
**Companion:** [`sc-xml.md`](sc-xml.md) (the class graph and command tables the string keys index into)

This is a reference document. Every table below is generated by parsing all **577 `.vs` files in
`data.pak` (577/577 parsed, 100%)** and walking the resulting ASTs. Nothing here is hand-curated
except the grouping headings and the notes.

A reimplementation of the engine must supply everything in these tables. That is the whole point
of the document: this is the size of the interoperability surface.

## The executable declares its own signatures — use them before this document

**Everything below is inferred from call sites.** It was extracted by parsing all 577
scripts and walking their ASTs, which gives exact names, exact arities and exact call
counts, and gives argument *types* only as a guess from what the corpus happens to pass.

`gbr.exe` carries the real thing. Interleaved with the host entry point names in its string
pool are their **C-style signatures, receiver and argument names included**:

```
RUType
int,  str strClass, int nRace
...
GetSettlements
Settlement, point pt, str type, int idPlayer
NearestStronghold
Settlement, point pt, int idPlayer, int fltPlayer
...
AIStart
void, int player, str profile, int difficulty
```

**The pairing is mechanical, and this document used to say it was not.** [^pairing] The names,
the signatures and the type codes are all *call arguments*, pushed as adjacent immediates at
the site that registers each entry point, and there are two registrars:

| Registrar | Call sites | Argument shape | Yield |
|---|---:|---|---|
| `0x00699d20` | 406 | `(fn, name, signature)`, `__thiscall` | 410 registrations (405 direct plus 5 through the wrapper at `0x0069a030`), **338** distinct `Receiver::Name` keys, **235** distinct signature strings |
| `0x00699bb0` | 1,058 | `(registry, fn, name, ret, argc, argtype…)`, cdecl | 1,058 registrations, **936** distinct keys, no signature string at all |

**1,272** distinct entry-point keys between them, and exactly **two** names are registered
through both: `EndGame` and `Squad::SetState`.

The numeric registrar's type codes are the same integers throughout, and the table of them can
be read straight off the registrations, because a member's first argument type is always its
receiver and the receiver is named in the key: `1 int`, `3 float`, `6 point`, `7 bool`, `8 rect`,
`11 str`, `20 Obj`, `21 Unit`, `22 Building`, `23 ObjList`, `24 Hero`, `25 Tower`, `26 Wagon`,
`27 Settlement`, `28 ItemHolder`, `29 Conversation`, `30 Item`, `32 Query`, `33 Barrack`,
`34 NamedObj`, `35 Druid`, `37 Ghost`, `38 Catapult`, `39 Sacrifice`, `40 SquadList`, `41 Squad`,
`42 GAIKA`, `43 Gate`, `44 Teleport`, `45 Ship`, `46 Flying`, `0 void`. Codes with `0x100` added
are out-parameters — the registrar masks the bit off at `0x00699c05` — which is how
`GetCmdCost`'s two `int`s and `CheckUEnabled`'s `mask` are declared.

The executable is ground truth for arity, return type and argument type in a way this document
is not, and it has already settled `SetCmd`, `ClrCmd`, all 33 GAIKA members, the `AIO_*` order
queue and the `Dipl*` family in minutes each. **Check it before inferring a signature from call
sites, and before refusing an entry point as unknowable.**

Where the two disagree, the executable wins and this document is wrong — which has happened
at least once already; see the `GetConst` row under *Where each key space is defined*.

## How to read the tables

- **Arity** lists every argument count observed. A member written without parentheses
  (`u.IsValid`) is recorded as arity 0, because the language treats it as a zero-argument call
  (see the language spec). Multiple arities mean the host entry point is overloaded or has
  optional trailing arguments — `AIVar` is called with 2 and 3 arguments, `SetCommand` with 1 and
  2, `Goto` with 4 and 5.
- **Returns** is inferred from `<typed local> = <call>` assignments across the corpus. A blank
  (`—`) means the result is never assigned to a typed local — usually a procedure, occasionally a
  value only ever used inline. Two types listed means the corpus assigns the result to both.
  **It is an inference, and two things make it wrong**: a script that narrows the result into a
  more specific local, and a name that is both a free function and a member (the extractor pools
  their return types). Ten rows had a return type the registrars contradict; they are now the
  registrars', each marked **bold** and footnoted [^types]. Every other typed row in both tables
  agrees with a type code or a signature string, bar four whose name no registration carries.
- **Receiver types observed** lists the declared types of the receiver expression, most frequent
  first, and omits receivers the analyser could not type (chained expressions and untyped
  locals). Absence of a type here is not evidence the method is unavailable on it.
- **Dominant argument types** is the most common statically inferred type per position, from the
  call sites only — nothing declares these. `const` means a bare global constant, `expr` means a
  computed value the analyser does not type further, `?` means the position is dominated by chained
  or call expressions, and a trailing `?` marks a position with no clear majority. Treat the whole
  column as a hint, not a signature.

**`AsTower` and `AsBuilding` are one function.** The registration block gives
them the same body address and two different return-type words, 0x19 (`Tower`)
and 0x16 (`Building`); the body's whole test is bit 23 of the object's first
flag word, which is the building bit. So the language has a `Tower` type and the
runtime has no tower test: a script that wants one asks `IsHeirOf` afterwards,
which is exactly what `OUTPOST_ATTACK_VERIFY.VS` does on the line after its
cast. The same is not true of the other thirteen, which have distinct bodies.

(0x004c6220, `int`) answers the clock's speed per mille, game `+0x1244`. `SetSpeed`
(0x004c6ce0, `void, int speed`) **changes nothing itself**: it builds a `CVXCmdSetSpeed` with the
local player as issuer and the argument unvalidated, and posts it through the local command path;
nothing is posted when game `+0x230` says the match fixed its speed. Here the command is
`NetOrderKind::set_speed` and the path is `HostContext::outbox` (`sim::OrderOutbox`): a
networked peer queues it for an agreed turn, a single-player match (`sim::LocalOrders`) applies it
at the head of its next turn, and execution clamps it to 1..100000 either way. With no outbox (a
headless run) it posts nothing, which is this engine's reading; the original always has a command
path. **The app does not run `SCDEBUG.XML`'s key bindings**, so the keypad `+`/`−`/`*` that call
these two are not wired; the entry points are ready for when something does.

`TogglePause` (0x004c6680, `void`) is registered by the executable but has **no call site** in
the installation, in a `.vs` file or an XML snippet, so it is not declared here and not
implemented. Recorded for when something needs it: it sends a `CVXCmdSetSpeed` of **1** to pause,
after remembering the current speed in a process global (0x00996850), and when the speed is 1 sends
the remembered speed back. Unlike `SetSpeed` it does not test game `+0x230`. The remembered speed
is not world state in the original (a global outside the game object), which is the part a
reimplementation would have to decide on.

**`AIStart/3`'s edges, read** (wrapper 0x00434f90, core 0x00434ca0; `f_ai_start` in
`sim/ai.cpp`). The wrapper checks the player (1..16), then the uppercased profile against the
profile list, then the difficulty (0..2, incremented to 1..3), and only then calls the core, so
**any refusal leaves a seat's existing AI running**. The core destroys a seat's existing AI before
building the new one, so **a second `AIStart` restarts** rather than stacks. **An empty profile is
refused**: the list is filled by walking `data/ai/`'s subdirectories (0x004433b0 → 0x00443190),
each adding its uppercased name, and the root is loaded without one. The core path is different
and takes any name, including the root: 0x00434de0 passes `"Default"` straight to it, and here a
map's own `@AI` and a dropped seat's takeover (`CommandBarSink::take_over`) reach the root the same
way. **Inferred:** since `data.pak`'s only profile directory is `DEFENSIVE`, the twenty shipped
`AIStart(…, "DEFAULT", …)` calls are refused in the retail game as they are here; the listing
function (0x0063a4a0) was not followed into the packs to prove it. This engine's session registers
only the root, not `DEFENSIVE`, which the original's list holds; nothing shipped names it through
`AIStart`.

### The `Env*` root scope, and the leading slash

Each of the six `Env*` names is registered **twice** in `gbr.exe`, once with a scope argument and
once without (0x006ae7b0 registers the six scope-less forms; 0x006ae941, 0x006ae839 and
0x006ae8bf the player, settlement and building forms). The scope-less form is the *root scope*,
and it is called **403 times** — 191 `EnvReadInt/1`, 164 `EnvWriteInt/2`, 34 `EnvReadString/1`,
14 `EnvWriteString/2` — every one of them in a container `Sequences/` script, and never once in
`data.pak`. `EnvReadObj/1` and `EnvWriteObj/2` are declared and called by nothing.

A scoped call's key is a bare name and the engine builds the path (`/<map>/Player%d/<key>`). A
root call's key **is** the path, and the leading slash is significant, not decoration:
`MakePath` at 0x006ab0e0 returns the string unchanged when it starts with `/` and otherwise
prepends the running script thread's `Context` — a `char*` the thread serialises under that name
(0x0069cc58), null unless the script was launched attached to an object, in which case it is that
object's id formatted `"%d"` (0x0041ccb0). So `"/Bonus"` and `"Bonus"` are two different slots
under every possible context, and nothing normalises either.

The corpus agrees: 75 of the 77 distinct root literals use one spelling for every read and every
write. The two that do not — `Bonus` in `Conquests/mediterranean.BFHP` and `En_Direction` in
`3_Great_Losses_Egypt.bfhp` — mix one-sidedly, which is a typo and not a convention. The cost of
the first is real and is reproduced rather than repaired: `Sequences/seq0.vs` writes `/Bonus` and
dispatches on it correctly, but `seq1.vs`, `seq3.vs` and `seq6.vs` guard their loops on
`EnvReadString("Bonus")`, so three of the seven conquest bonuses never run in the retail game.
Pinned by `tests/test_corpus_env_paths.py`.

not the word: it is `test`/`setne` and its registered return type is 7.

`UnitFlags` attribute, set on 14,586 of the retail install's 16,171 units and
clear on every wild animal without exception. See `docs/formats/map.md` under
**Unit**, which names bit 22 (`Flying::IsInAir`) from the same attribute and
carries the other three as open.

## Implementation order

Frequency-ordered, the cheapest useful milestones:

1. **Language core** — the grammar, `int`/`bool`/`str`, locals, control flow, coroutines with
   `Sleep`. Nothing runs without it.
2. **`Obj` + `Unit` + `ObjList`** and the top 20 members (`IsValid`, `count`, `player`, `pos`,
   `settlement`, `AsUnit`, `IsAlive`, `AddCommand`, `AsBuilding`, `SetCommand`, `ClearDead`,
   `GetCentralBuilding`, `IsEnemy`, `InHolder`, `hero`, `AsHero`, `stamina`, `command`, `x`,
   `health`). That is 5,719 of 12,219 member call sites — 47%.
3. **The top 10 free functions** (`Sleep`, `SetAIVar`, `rand`, `AIVar`, `EnvReadInt`,
   `EnvWriteInt`, `IsResearched`, `pr`, `GetConst`, `Translate`) — 2,853 of 4,912 free call
   sites, 58%.
4. **`Settlement`, `Building`, `Query`** — unlocks all the `SUBAI` command scripts.
5. **`Squad`, `SquadList`, `GAIKA`** — unlocks `DATA\AI`, i.e. the actual opponent.

## What is still unknown

- **Argument types are inferred, not declared.** The "dominant argument types" column is a
  statistical summary of call sites. Where a position is dominated by chained expressions it reads
  `?`. Nothing in the corpus declares a host signature, so every arity/type here is a lower bound
  on what the real entry point accepts.
- **Optional versus overloaded arguments.** `AIVar` appears with 2 and 3 arguments, `SetCommand`
  with 1 and 2, `Goto` with 4 and 5. Whether these are optional trailing parameters, overloads,
  or variadics is undetermined; `AIRun` is certainly variadic.

  **`Eval` and `Count` are settled and are not one family.** `Eval` at 0 arguments is
  `Squad::Eval`, a property; at 6 it is a free function taking a point and a range. The GAIKA
  forms are genuine overloads — `gbr.exe` registers four separate bodies for `GAIKA::Eval`
  (0x0042f1a0, 0x0042f3d0, 0x0042f670, 0x0042fc40) and two for `GAIKA::Count` — sharing a
  census and differing in how it is reported: the 6-argument form writes four `int`s by
  reference in the order `own, ally, enemy, enemy_hidden`, the 3-argument form returns one
  total selected by a side mask, and the 2-argument form returns the *own* total. `Count` at 1
  argument is `Squad::Count(class)` and at 0 is `ObjList::count`.

  **The player argument of the GAIKA family is 1-based**, which is worth stating because
  nothing in the call syntax says so: `GAIKA::GetSquads` (0x00439500) `dec`s it at 0x004395a5
  before the membership loop, and every shipped site passes `AIPlayer`, which `AIGetPlayer`
  returns 1-based.

  **`GAIKA::Count/3`'s first argument is still undetermined**, and the corpus cannot settle it:
  the two live sites write `gaika.Count(AI_ENEMY, AIPlayer, "Peasant")` and a commented-out
  line writes `gaika.Count(AIPlayer, AI_OWN, "GDruid")`, and the values cannot tell the two
  readings apart because `AI_ENEMY` and `AI_STAYING` are both 4. 0x004330b0 pops in the
  registered order, so the positions are `(mask, player, class)`; what it does with the mask —
  it tests bit 0 and then requires bit 2 of a presence classification — was not read to the end.
- **The three population writers do not agree about the ceiling, and the difference is
  observable.** `Settlement::SetPopulation` (0x005c2200) stores `min(value, max_population)` --
  a signed compare against `settlement + 0x4c` before the write to `+0x50` -- while
  `AddToPopulation` (0x005c2250) is one `add` with no clamp at all and `AddToMaxPopulation`
  (0x005c2290) is one `add` to the ceiling itself. The late desync dumps showing `101 100` and
  `165 150` are what an uncapped `AddToPopulation` produces and are not evidence about
  `SetPopulation`; `TOWNHALL_ADDPOP.VS` and `PEASANT_ENTER.VS` are the sites that get a
  settlement past its ceiling. `ONFINISH_RESEARCH.VS` is where all three meet: "Free Beer" is
  `SetPopulation(population + 20)` and stops at the ceiling, "Housing" is
  `AddToMaxPopulation(20)` and moves it.

  Neither `add` clamps at zero either. The floors in this engine are its own and no shipped
  call site can reach one.
- **`NearestStronghold`'s player argument is 1-based and its filter has three values, not a
  mask of many.** All three arities funnel into 0x0042da70; the wrappers decrement the player
  **unconditionally**, so `NearestStronghold(pt, 0)` asks about player −1 and the search reads a
  negative player as *no filter at all* — which is exactly what the executable's own
  one-argument form passes. The two-argument form writes in `AI_OWN` (the literal 1), so the
  short spelling means "my nearest stronghold". The relation code (0x0044e250) answers exactly
  one of `AI_OWN` 1, `AI_ALLY` 2, `AI_ENEMY` 4, reading the caller's **own** diplomacy row and
  never the transpose. A player index that is merely out of range leaves the filter on and
  matches nothing, which is a different answer from disabling it.

- **`Obj::OpenItemHolder` is a contents transfer, and its bool is "something moved".** 0x0053c350
  walks the holder's slots **downwards**, moving each item into the receiver until the receiver
  is full, and destroys the holder afterwards if it ended up empty and its class declares
  `delete_empty="1"`. The `"ItemGotFromHolder"` call beside it (0x005a93a0) is a floating
  on-screen caption gated on the local camera and the local player's fog — the only user
  interface on the path, and nothing about the result depends on it. There is no distance check:
  both shipped sites `Goto` the holder first.

- **`Settlement`'s food reserve is three `Env` ints and two entry points.**
  0x00425890 computes it as
  `Reserve > 0 ? ((GoldSpentOnArmy - ReservedAt) * Reserve) / 100 : 0`, and all three terms live
  under the settlement's own scope with a **zero-based owner suffix**:
  `/<root>/Settlement<id>/Reserve<owner>` (0x007ad71c), `GoldSpentOnArmy<owner>` (0x007ad6d4)
  and `ReservedAt<owner>` (0x007ad738). `Settlement::StopReserving` (0x00425980) writes a 0 into
  the first and does nothing else; `Settlement::ReserveFor(cmd, percent)` (0x0042cd60) is what
  sets it, and is not implemented here. The `ReserveFor<player>` key the scripts read with
  `EnvReadString` is a *different*, script-written string key — `ESH_MARKET.VS` writes and reads
  it itself.

- **`Obj::IsRanged` is a class-property test, not a range comparison.** 0x0053f5b0 reads the
  class descriptor's `std::string` at `+0x960` and answers true when it is non-empty and not the
  literal `"**Invalid**"` (0x007ae000) — the original's uninitialised-string default rather than
  an authored value, and no shipped class declares it. **Which attribute fills `+0x960` is not
  settled.** The class reader writes `projectile_shadow` into `+0x97c` and `projectile_fire` into
  `+0x998`, and nothing in the image writes `+0x960` with that displacement; the string
  `_projectile_class` at 0x007c8650 is evidently composed with a prefix at run time. What *is*
  read: the constructor at 0x005a6c9d seeds a stride-0x1c run of strings at `+0x928` … `+0x998`
  with the sentinel, 0x0059c7c8 inherits each from the parent class while it is still the
  sentinel, and 0x005b1d20 resolves `+0x960` **as a class name** and reads a range-like number
  off the class it names. `projectile_class` is the reading taken;
  `building_projectile_class` is the alternative, and the two differ for a tower.

- **`Unit::Idle` and `Unit::Taunt` are the same function, and both cost their argument.**
  0x005d6030 and 0x005d60f0 differ in one byte: the activity constant they pass to
  0x005a7680, 4 for an idle and 5 for a taunt. Both are `(Unit, int)` on the suspend registrar,
  and both branch on the receiver's *position*: `(-1, -1)` — the constant pair at 0x008212bc /
  0x008212c0, `0xffffffff` with no writer in `.text`, which is what a unit inside a holder
  reads — suspends for the argument (return 1) and returns 0 on the resume, and anything with a
  real position pops the arguments, sets the activity, drops the combat target and returns 3.

  A 3 from a suspending entry point (the dispatch table at 0x0069dbc4) means *the call is
  done, but end the slice*: the call is stepped over as a 0 is, the slice's wait cell is set
  to -1 and its budget forced out (0x0069d5fb), and the scheduler takes a coroutine whose wait
  is -1 off its timer queue altogether (0x0069f842 → 0x00687bf0). The object wakes it. For
  `Idle` and `Taunt` that is the unit's idle-and-taunt activity (0x005d2ca0), which takes its
  budget from the stack slot just above the script's stack pointer — where the popped argument
  still lies, the pop being made before the activity is set — spends it on the pose and on
  fidget animations in 100 ms steps, and wakes the script when it is spent (0x005d2de0 →
  0x0069f8f0). `Ship::Idle` writes its own duration into that slot before it returns 3, which
  is the same mechanism read a second way. **So the `2000` every shipped `Taunt` site passes is
  a two-second taunt, on the map as much as in a holder**; an earlier reading here, that the
  on-map branch costs one scheduler step and only the held branch consumes the argument,
  missed where the activity's budget comes from.

  `Unit::Idle` is registered **once**, at arity 1; the arity-0 `Idle` in the corpus is
  `Ship::Idle` (0x005c6ea0), a different function that sets the `ForceIdle` flag and supplies
  the duration itself. Not reproduced: the fidgets are drawn from the synchronised generator,
  so an idle or taunt on the map spends random draws in `gbr.exe` that this engine does not.

- **The four team scores share one shape and one half-known term.**
  `GetTeamMilitaryScore/1` (2 sites), `GetTeamOverallScore/1` (4),
  `GetTeamPowerScore/1` (0) and `GetTeamAchievementsScore/1` (0) all take a **1-based** player,
  build the same team through 0x00522e20, and average one per-member expression over it. The
  team is the alliance matrix in both directions -- `PlayerTable::are_allied` -- with the caller
  inserted first and unconditionally, and **the scan for the others covers only the first eight
  player slots** (`esi < 0x1900` over a `0x320` stride; the `cmp esi, 0x3200` inside the loop is
  dead). The per-member terms are `military_rating`, `power_score * military_rating / 100 +
  gold_used / 1000`, `power_score`, and `gold_used / 1000`.

  **`power_score` (0x0056a8c0) is the term that is not settled.** It is
  `(bucketB / 2 + garrison_power + field_power + bucketA) / 100 + 20 * townhalls + 3 * other
  settlements`, where the two power terms are sums of a per-unit
  `((attack + defence) * (level + 13) * (maxhealth / 4 + health)) / 1000 + 1` (0x004439d0) and
  the two buckets are headcounts read off a per-object component at `+0x1cc`, split on a mode
  flag at `+0x1d4` whose meaning was not recovered. It is also **cached and not always
  recomputed**: 0x0056a8c0 recomputes only while the player's slot state (`+0x290`) is 1, and
  returns the last stored value once the player has won or lost.

  **All four fault on an out-of-range player.** The entry point converts, gets a null record for
  anything past slot 15, and 0x00522e20 dereferences it at `+0x64` with no check.
- **Which arguments are written through.** `Eval`, `GetSquads`, `ParseStr` and `TSHeroRecruit`
  all write into caller locals. There is no marker in the call syntax. Every host entry point
  needs its in/out signature established individually.

  `TSAdvHeroSkills` was on that list and does not belong on it: both its arguments carry the
  by-reference bit (type 268) and the helper it runs only ever *reads* them. The bit is how the
  language passes a growable array at all, not a claim that the callee writes one — which is a
  distinction the call syntax cannot make and the registration alone does not settle either.
- **Receiver typing for 45 members** (listed above) could not be established statically.
- **`Subtract` versus `Substract`.** Both spellings appear as free functions (8 and 2 call sites).
  Either the engine exports both, or one of the two scripts is dead. `DATA\AI\ESH_MARKET.VS` and
  `DATA\AI\GS_CAPTURE.VS` are among the users, and both are live, so both spellings probably exist.
- **`Attack`/`attack`, `Count`/`count`, `Player`/`player`, `GetGAIKA`/`GetGaika`.**
  These case variants may be one host entry point each (case-insensitive lookup) or two. In every
  corpus site the pairs are separated by arity or by receiver type, so both readings work.

  **`Size`/`size` is settled and it is worth stating what settled it.** `gbr.exe` registers the
  name four times — `Squad::Size` (0x00422ca0), `SquadList::Size` (0x0042bc40), `IntArray::size`
  (0x00697f20) and `StrArray::size` (0x00698070), plus a fifth on `StrMap` the corpus never calls
  — so it is *four* entry points distinguished by receiver alone, at one arity, with no arity to
  separate them. A host registry keyed case-insensitively on `(kind, name, arity)` therefore has
  one slot for all four and has to branch on the receiver inside it. The argument codes name the
  receivers: 41 `Squad`, 40 `SquadList`, 268 and 269 being `IntArray` and `StrArray` with the
  by-reference bit. `Squad::Size` reads `[squad+0x50]`, the `_Mysize` of the membership deque
  whose header starts at `+0x40` — the same deque `Squad::Count` walks — so it is the number of
  members and cannot disagree with a count over them.
- **Constant values.** The numeric value of every `AI_*`, `SS_*`, `SF_*`, `GS_*`, `ES_*`, `TS_*`,
  `hs*`, `gs*`, `c*` and race constant is unknown; only the names are recoverable from script. The
  `+`-combination idiom (`AI_COMING + AI_STAYING`) constrains the `AI_*` family to disjoint bit
  values but says nothing about the rest.
- **`AIV_*` semantics.** 113 tuning variables, of which only about 30 are read as well as written.
  The remaining ~80 (`AIV_MaxRHastatus`, `AIV_MaxGSwordsman`, …) are written by the difficulty
  setup and presumably consumed inside the engine, not in script.
- **`GAIKA`, `LAIKA`, `MAIKA`.** The three AI spatial abstractions are named but their exact
  relationship (`GAIKA.LSA`, `IsWaterLsa`, `CheckLsaPath`, `SetMAIKA`, `CheckMAIKA.vs`) is only
  partly recoverable from usage.
- **`Query` liveness.** `Query` results appear to re-evaluate (`WaitNonEmptyQuery` blocks until a
  query becomes non-empty), while `ObjList` is a snapshot needing explicit `ClearDead`. The exact
  invalidation rules are unknown.

[^selection]: **The player id these carry is a guard, not an index, and two of them are about
    something else entirely.** All nine `ClearSelection` sites in `data.pak` pass a player
    (`ClearSelection(wagon.player)`) and all ten `Select` sites do too, which reads as one
    selection per player. It is not. `ClearSelection` (0x005a8120), `Obj::Select` (0x005abfc0)
    and the two-argument `Obj::Deselect` (0x005ac060) each turn the argument into a pointer to
    that player's record, compare it against the pointer the globals block keeps at `+0x12c8` —
    the local player's — and return having done nothing when they differ. There is one
    selection, the machine's own, which is why it is not part of the sync state and could not be.
    The no-argument `Obj::Deselect` (0x005ac0e0), the only form the corpus calls, makes no
    comparison at all.

    `SwapSelectedObj(from, to)` (0x004c84e0) is **remove and append**: it asks whether `from` is
    selected, removes it through Deselect's helper and runs Select's helper on `to`, which
    appends. The summoned wolf lands at the end of the selection; the druid's position is not
    kept.

    `IsSelectionAssigned` and `WasSelectionAssigned` are **not about the selection**.
    `Is` (0x004c6aa0) bounds its player to 1..16 and walks ten numbered control groups at
    `record + 0xac`, stride 0x2c, answering true at the first non-empty one — which is the
    evidence for ten slots in `ShortcutTable`. `Was` (0x004c6a00) reads the registry key
    `/Player<n>/SelectionAssigned` and answers whether any bit is set; the bit is set by the
    input layer when the *player* assigns a group, and by nothing in script, which is what
    `TUTORIALS\GENERALADVICE6.VS` is discriminating when it nests the two. Both have
    two-argument forms in `gbr.exe` that name a single group and that no shipped script calls.

    That key is the one registry path in the binary with no `/<map>/` prefix — every other
    player-scoped key is `/%s/Player%d/...` — so it is root-scoped and outlives the map.

    **`GetSelection/0` is a name `gbr.exe` never registers.** It is in this document because
    `DATA\SUBAI\DEBUG_DUMP.VS` calls it, and the string pool holds `_GetSelection` and nothing
    else. That one call site cannot ever have run past its first line, so the entry point is
    left declared and unimplemented on purpose. See
    [`sim/orders.hpp`](../../engine/core/include/imperivm/core/sim/orders.hpp).

[^endgame]: **The three-argument form is invisible to this document and is the one the campaigns
    use.** Every table here is generated from the 577 `.vs` files in `data.pak`, and all 24
    `EndGame` sites there pass two arguments. The 24 shipped `.bfhp` containers — every adventure
    and the conquest — hold 61 more, and every one of those passes three:
    `EndGame(1, true, Translate("Scipio Africanus has died."))`.

    That is not a VM tolerating surplus arguments. Across all **885** `.vs` files in the install,
    `EndGame` is the *only* name called with more arguments than some other site gives it. It is a
    second registration: `gbr.exe` registers the name twice, once through the signature-string
    registrar (0x00699d20, `"void, int player, bool lose"`, body 0x004c9610) and once through the
    numeric registrar (0x00699bb0, type codes `[0x00, 0x03, 0x01, 0x07, 0x0b]`, body 0x004c9660).
    Both bodies end the game through the same virtual slot 0x48; the second additionally keeps the
    string, and only when the player it names is the local one. See
    [`sim/match.hpp`](../../engine/core/include/imperivm/core/sim/match.hpp).

    The lesson generalises: an arity in this document is a lower bound on the surface, because a
    container-only entry point or a container-only arity leaves no trace in `data.pak`.

[^pairing]: **This section used to say the name/signature pairing "is not mechanical and cannot be
    read off by position alone", and that the string pool held "at least 271" signatures.** Both
    are wrong, and the second is a consequence of the first: counting strings in the pool
    undercounts because identical signatures *are* deduplicated there — but nothing has to be read
    off the pool. Every registration is a call, and its name, signature or type codes are the
    immediates pushed at the call site.

    Enumerate them with a byte scan for `E8 rel32` whose target is the registrar, and decode
    backwards from each hit to the enclosing function's `CC CC` alignment padding. That yields
    406 sites for `0x00699d20` and 1,058 for `0x00699bb0`, exactly, with no misses and nothing to
    guess at. Control: 1,058 of 1,058 numeric sites and 405 of 406 signature sites decode to
    literal immediates, and the one that does not (`0x0069a044`) is a forwarding wrapper —
    `0x0069a030`, called five times, which passes its own arguments through and then flags the
    entry it just registered. Nothing in the scan is ambiguous or partial.

    So the count is not "at least 271": it is **235** distinct signature strings over **338**
    signature-registered keys, beside **1,058** numeric registrations over **936** more, and the
    two tables between them name **1,272** distinct entry points. (*Types*' count of 29 is a
    different question — types the *corpus* declares locals of — and stands. Six more appear only
    in the registrations and so are absent from that table: `void`, `float`, `Conversation`,
    `Ghost`, `NamedObj` and `StrMap`.)

[^types]: **A return type in this document is what the corpus assigns the result to, and that is
    not the same question as what the entry point returns.** `Unit u = .BestTargetInRange(pt, r)`
    proves a `Unit` local exists, not that the host returns one; the registration at `0x005dfbba`
    says `ret = 0x14`, `Obj`. Two things make the inference wrong, and between them they account
    for **ten** rows out of the 185 free and 520 member ones — audited exhaustively against both
    registrars, not spot-checked. With them corrected, all **280** typed rows agree; four cannot be
    checked at all because no registration carries their name (`Choose`, `GetSelection`, member `Goto`, member `Consume`);
    the rest declare no type.

    **Three rows: the extractor pools a free function and a member of the same name.**
